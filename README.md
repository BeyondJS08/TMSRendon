# TMSRendon (TMS + ERP + IMS)

---

**TMSRendon** is an enterprise-grade Transportation Management System (TMS), Enterprise Resource Planning (ERP) and Inventory Management System (IMS) built specifically for terrestrial logistics and cargo transport company in Mexico named TransRendon (handling trucks, tortons, and heavy transport units).

---

## Project Structure

This project uses a monorepo layout:

## Technical Stack

### Core Technologies
*   **Frontend:** [Next.js 16](https://nextjs.org/) (React 19, Tailwind CSS 4, [shadcn/ui](https://ui.shadcn.com/), React Query/TanStack Query)
*   **Backend:** [NestJS 11](https://nestjs.com/) (TypeScript, Express)
*   **Database:** [PostgreSQL](https://www.postgresql.org/) + [PostGIS Extension](https://postgis.net/) (Spatial/Coordinates tracking)
*   **ORM:** [Prisma](https://www.prisma.io/) (Database queries & migrations)
*   **Caching & Queues:** Redis + [BullMQ](https://bullmq.io/) (Asynchronous jobs)
*   **Infrastructure:** Docker/Podman (Self-hosted Database, Caching & Engine)
*   **Authentication:** Supabase Auth (GoTrue API)

### Localized Integrations (Mexico & Fleet Telematics)
*   **Taxes & Invoicing (SAT):** Facturama API (CFDI 4.0 & Complemento Carta Porte 3.0/3.1)
*   **Accounting Sync:** CONTPAQi-compatible layouts for direct journal sync
*   **Fleet Telematics:** Samsara / Geotab API (Real-time GPS tracking and odometer data)

## Architecture & Development Approach

### 1. Modular Monolith
To keep development fast and prevent microservice orchestration overhead, all codebases reside in this single repository. Concerns are strictly isolated by module folder inside `backend-tms/src/modules/` (e.g., `operations`, `hr`, `invoicing`, `maintenance`). Modules must only communicate with other domains via well-defined internal services/interfaces.

### 2. API-First Design
All endpoints are RESTful, validated, and documented using OpenAPI/Swagger. Frontend components are built strictly against backend DTO specifications. 
External services must be consumed through dedicated interfaces using the **Adapter Pattern** (e.g., `SatAdapter` for SAT invoices, `TelematicsAdapter` for GPS systems) to allow swapping providers seamlessly.

### 3. Event-Driven Asynchronous Processing
Heavy and error-prone external communications are offloaded to Redis background queues powered by **BullMQ**:
*   CFDI xml generation, SAT validation, and timbrado.
*   Processing GPS telemetry heartbeats.
*   Calculating payroll taxes and IMSS retention.
*   Maintenance reminders and safety alert triggers.

### 4. Idempotency & Retries
Every external API write operation (such as invoice timbrado) must include an `Idempotency-Key` header generated by the frontend. In case of timeouts, BullMQ implements exponential backoff retries with a Dead-Letter Queue (DLQ) to ensure no double-stamping or double-charging occurs.

## Setup & Execution Guide

### Prerequisities
*   Node.js v20+
*   pnpm (v9+ recommended)
*   Docker or Podman (for running database & Redis locally, optional if using hosted Supabase)
*   A Supabase project (for Auth and PostgreSQL)

### 1. Database & Caching Setup
1.  Ensure you have Docker/Podman running if you are using the local Supabase stack.
2.  Spin up the local PostgreSQL + PostGIS and Redis services (or point to your Supabase-hosted instance).
3.  Configure your environment variables (see step 2).

### 2. Environment Variables

Create the following env files:

**Root `.env`** (used by Prisma):
```env
DATABASE_URL="postgresql://postgres:postgres@127.0.0.1:54322/postgres?schema=public"
```

**`frontend-tms/.env.local`**:
```env
NEXT_PUBLIC_SUPABASE_URL=https://<your-project>.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=<your-anon-key>
```

**`backend-tms/.env`**:
```env
PORT=8080
DATABASE_URL="postgresql://postgres:postgres@127.0.0.1:54322/postgres?schema=public"
SUPABASE_URL=https://<your-project>.supabase.co
SUPABASE_ANON_KEY=<your-anon-key>
SUPABASE_JWT_ISSUER=https://<your-project>.supabase.co/auth/v1
SUPABASE_JWT_AUDIENCE=authenticated
```

### 3. Prisma Database Schema
Generate the database client and apply migrations:
```bash
# From the root directory
npx prisma generate
npx prisma db push
```

### 4. Running Backend (NestJS)
```bash
cd backend-tms
pnpm install
pnpm run start:dev
```
The backend API will run on `http://localhost:8080` (or configured port). Access API Docs at `/api/docs`.

### 5. Running Frontend (Next.js)
```bash
cd frontend-tms
pnpm install
pnpm run dev
```
The client app will be accessible at `http://localhost:3000`.

### 6. Auth Flow
1.  Visit `http://localhost:3000/login`.
2.  Sign up with email/password (handled by Supabase Auth).
3.  Log in; you will be redirected to `/dashboard`.
4.  The dashboard calls the backend with the Supabase access token; the backend validates the token via Supabase JWKS.

## Mexican Fiscal Compliance (SAT & CFDI 4.0)

Under Mexican tax law, all terrestrial cargo transportation must be backed by a **Complemento Carta Porte 3.0/3.1** attached to an electronic invoice (CFDI de Ingreso or Traslado).
*   **PAC API Integration:** We use Facturama to compile, sign, and stamp XML files.
*   **Validation Layer:** Prior to sending payloads to the PAC, the NestJS `InvoicingModule` executes schemas to validate critical fields:
    *   *RFC Validity* for clients, operators, and landlords.
    *   *ClaveProdServ* (Product/Service Keys) and *ClaveUnidad* (Unit Keys).
    *   *Configuración Vehicular* (SCT truck layout code) and *Permiso SCT*.
*   **Security:** PDF/XML outputs are stored securely in Supabase Storage with metadata indexed in PostgreSQL for auditing.
